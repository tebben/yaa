## Layout, panels and keyboard model

Lands in: M1. The vim layer: Later; the editor's vim keys: M3.

This file says what the shell does. How it looks (colours, borders, focus styling) is in `docs/design/ui.md` and `docs/design/tokens.json`.

The window is a fixed shell around a user-arrangeable grid: a header across the top and a footer across the bottom, and between them a left menu and the grid of panels. The header and footer show information for the selected project and worktree.

**Shell**

- **Left menu:** the project list, hidden and shown again with Ctrl B or the button that leads the header. Each project expands to its main checkout, marked as the default branch, and its worktrees, each with a state badge (see `02-worktrees.md`); a collapsed project shows how many worktrees it has. Selecting a project opens its overview; selecting a worktree opens its grid, and the panel bar shows only then. A search field above the list, focused with / while focus is outside the grid or no panel is open, filters it as you type with the palette's matching: a project whose name matches keeps all its worktrees, otherwise only the worktrees whose branch matches show. Enter moves to the first result, Escape clears the search and moves to the list. The add button opens the system's folder picker. A hovered project shows a new worktree button and a remove button, which takes it off the list as the palette's Remove project does; a hovered worktree shows a finish button. These buttons take no tab stop: keys reach the same through the palette.
- **Header:** leads with a button that hides and shows the left menu and the name "yaa" in the wordmark's Geist (`docs/design/ui.md`), both in the same place whether the menu is open or not. Then the current project and worktree, with slots on the left, centre and right that plugins can fill, and at its end the panel bar.
- **Footer:** slots for plugins, plus core info for the selected project: branch, uncommitted change count, ahead/behind. Plugins add chips for agent state, cost and PR status.
- **Centre grid:** every panel is a view contributed by core or a plugin (id, title, icon, component). Users drag panels to rearrange, split, tab and resize them. A layout is saved per project, with a default layout for new projects (changes on the left, the editor with the terminal under it, chat on the right) and a reset action. A saved layout that no longer reads as one (from an older dock version, for example) gives way to the default. A panel whose kind nothing provides any more, such as one from a removed plugin, keeps its place and says so.
- **Sizes:** adding, removing or moving a panel never resizes the panels it leaves alone in proportion to each other. A panel opened at an edge of the grid takes its room from the others in proportion to their sizes; a closed panel's room goes back to its neighbours the same way; a panel dropped on another panel's edge splits that panel in half (`docs/decisions/0033-dock-proportional-sizing.md`).

**Panel bar and panels**

- **Panel bar:** at the end of the header, one icon per panel kind (files, changes, chat, terminal, review, usage, workflows) that toggles the panel, with the open ones marked and a tooltip with the shortcut (`docs/decisions/0034-panel-bar-in-the-header.md`). Opening a closed panel places it at the right edge of the grid, spanning its height, as wide as it was when it last closed alone in its group while the app ran, and flashes it once. While an open panel's icon is pointed at or has focus, that panel shows where it is with an accent edge over a faint tint, and its tab too when it shares a group. Plugins add their own icons.
- **Panel header:** a small header with an icon, a title, a menu and a close button, so every panel can be closed with the mouse. Panels with a single purpose, such as the editor, show tabs instead of a title. Panels that share a group show as a strip of tabs that looks like the editor's file tabs.
- **Closing by keyboard:** Ctrl W closes the focused tab, and the panel when it has none, while focus is in the grid. In a focused terminal Ctrl W goes to the shell, where it deletes a word (see Keyboard model).
- **Focus:** exactly one panel is focused and is styled as `docs/design/ui.md` describes. The footer shows the input mode, for example NORMAL when the vim layer is on. Focus moves with directional keys.
- **Focus regions:** keyboard focus moves between the panels of the grid and the shell's regions: left menu, header (with the panel bar) and footer. The focus edge shows only after a key moved focus: the focus and list keys, and the tab keys. A click anywhere, or Escape, hides it until a key moves focus again; Escape is bound to hiding it only while it shows, so it reaches everything else otherwise. A region holding focus while the edge shows gets the same edge as a focused panel, and the grid's edge gives way while it does. Inside the menu, J and K move between items; inside the header and footer, H and L. The focused item is marked. Coming back to a region or a panel lands on the item that had focus there last, or on its first item that is not a text field when none had, or on the region or panel itself when it has none.
- **Text fields:** keys typed in a text field, such as the menu's search, the files filter or the chat's prompt, are text. Escape leaves the field for the panel or region holding it, where keys such as J and K act again, and I goes back to the field it left, or its first. A panel's own Escape binding comes first where it applies, such as the menu's search, which clears and moves to the list. Leaving a field is remembered: coming back lands on the panel or region, not in the field. Monaco, the vim status line and the terminal keep Escape (see Passthrough).
- **Default keys:** Ctrl H, J, K and L focus the panel to the left, below, above and to the right: the nearest panel past that edge that shares some of its length, so a wide panel reaches either of two narrower ones above it; past the edge of the grid they go on to the left menu (skipped while hidden), the footer and the header. Shift H or K and Shift L or J go to the previous and next tab of the focused panel, wrapping around; they work in the grid only, and not while a text field has focus, where they type capitals. Ctrl Shift H and L make the focused panel narrower and wider, Ctrl Shift K and J shorter and taller, by 5% of the grid. Opening or closing a panel while focus is outside the grid, such as on the panel bar, leaves focus where it was. While focus is in the grid (the palette gives it back before a command runs), closing the focused panel focuses the panel that takes its place and opening one focuses it; closing a panel that is not focused leaves focus where it was.
- **Icons over text:** settings, plugins, close, add, search and similar controls are icon buttons with a tooltip that shows the shortcut. Text labels are for content, not for chrome.

**Command palette**

- One keystroke opens it, Ctrl Shift P by default. A command that needs a choice, such as a new worktree's start branch and name, or how far to finish one, asks for it in the palette as a next step, with its own placeholder, notes above the list and items; Enter takes the selected item and Escape cancels. It lists every registered command that has a title and whose `when` condition holds where the palette was opened (project, worktree, focused panel), each with its first key and its category. Typing filters the list: the typed characters must appear in order in the category and title, case and spaces ignored, and a run of characters or a match at the start of a word ranks higher. The arrow keys, Ctrl J and K, and Ctrl N and P move the selection, Enter runs the selected command after the palette closes and focus has returned, Escape or a click outside closes it. These keys are commands too, bound with `when: palette.open`.
- Plugins register commands, and may register a settings page that the palette's settings entry lists next to core settings. Plugin settings are rendered from a schema by default, or from a custom panel.

**Keyboard model**

- Every action is a command with an id. Keybindings map keys to command ids, and users can override them. Components never attach their own key listeners; Monaco and the terminal are the two exceptions below.
- **Focus contexts:** each keybinding has an optional `when` condition over context keys such as `panel.kind == terminal`, `editor.focus` or `vim.mode == normal`, like VS Code's `when` clauses. A condition is keys combined with `!`, `&&`, `||` and parentheses (`&&` binds tighter), and `key == value` or `key != value` with a bare or single-quoted value; a key on its own holds when its value is true or a non-empty string. A command can have a `when` too: it runs, and the palette lists it, only while that holds. A key resolves to the first binding whose condition holds and whose command is registered and can run, so a binding to a command no plugin provides does not take the key. Core context keys: `panel.kind` (the active panel's kind), `focus.region` (`menu`, `header`, `dock` or `footer`; `dock` when nothing has focus), `focus.list` (`vertical` or `horizontal` in a shell region), `inputFocus` (anything keys type into has focus, Monaco included), `textField` (a text field has focus, Monaco not included), `focus.highlight` (the focus edge shows), `palette.open`, `project.selected` (a project is selected), `worktree.selected` (a worktree other than the main checkout is open) and `worktree.done` (the open worktree shows Done). Plugins add context keys under their namespace.
- **Passthrough:** Monaco and the terminal receive keys first. Each declares the keys it gives up to the app, for example the palette key and panel-focus keys. Every other key, Ctrl W and Ctrl C in a terminal included, stays with the widget. The list is a setting, so a user can take a key back, or give up one they bound themselves. The terminal's is `keyboard.terminalAppKeys`, by default the palette key, Ctrl H, J, K and L (focus), Ctrl Shift H, J, K and L (resize), Ctrl Shift N and Alt J, K and A (worktrees), and the terminal's own keys but paste (see `07-editor-files-terminal.md`).
- Electron's default application menu is replaced, so its accelerators do not take app keys.
- Focus moves between panels with directional keys, and within a panel by the panel's own navigation (lists, trees and tabs share one navigation helper).
- An optional vim layer adds modal navigation in lists and trees. The editor's vim keys are separate (see `07-editor-files-terminal.md`).
- Anything reachable with the mouse is reachable with the keyboard; this is a release criterion for each panel.

## Theming

Lands in: M1 for tokens and the dark theme; M6 for the light theme, the OS setting and user themes; VS Code theme import: Later.

One theme restyles the whole app: shell, panels, Monaco, code blocks in chat, diffs and the terminal.

- **Tokens:** all styling reads semantic CSS variables generated from `docs/design/tokens.json`: surfaces, text, borders, accent, focus, the worktree state colors (idle, running, attention, error, done), diff added, removed and changed, plus radius, spacing, sizes, font family and sizes, and density. Tailwind's theme maps to these variables, so components use semantic utilities such as `bg-surface` and never raw palette colors.
- **How tokens reach the app:** `pnpm run tokens` writes `packages/ui/theme.css`, a Tailwind `@theme static` block, and `packages/ui/tokens.ts`, the `TokenName` type; `check:tokens` fails when they are out of date. Each group lands in the Tailwind namespace that makes its utilities: colors in `--color-*` (`bg-surface`, `text-text-soft`, `bg-state-running`), font sizes in `--text-*`, line heights in `--leading-*`, radii in `--radius-*`, shadows in `--shadow-*`, and both space and size in `--spacing-*` (`p-2`, `p-0.5`, `h-row`); camelCase keys become kebab-case and a dot becomes `_`. Every variable is emitted, so plugin styles can read any token with `var()`. Tailwind's default theme is not loaded, so palette colors and off-scale sizes have no utilities. Density is left out until a second density ships.
- **Theme file:** a `theme.json` declares a name, a kind (light or dark), token values, a Monaco theme, a Shiki theme and a 16-color terminal palette. Missing tokens fall back to the built-in base theme, so a theme can be a short list of overrides.
- **Built-ins:** one dark and one light theme, with a setting to follow the operating system.
- **Loading:** themes live in a user themes folder, optionally per project, and are applied at runtime by setting the variables on the root element, with no restart. Plugins can contribute themes through a `themes` contribution point.
- **Rule for plugins:** plugin UI uses tokens only. The design system exports the token names as types, so a misspelled token fails the typecheck.
- **Later:** VS Code color themes as an import source. Shiki reads that format; Monaco needs a conversion step, to be checked.
